Technical debt: speed today, interest tomorrow.

“Shipping first time code is like going into debt. A little debt speeds development so long as it is paid back promptly with a rewrite.”

Ward Cunningham, The WyCash Portfolio Management System (1992)

The loan

Shortcuts to ship sooner: fewer tests, less cleanup, temporary fixes.

The interest

Every later change costs more: more bugs, slower development, customers who leave.

In the game. Rushed development piles up debt and bugs; debt slows development, and refactoring 10% or 25% of the time pays it down.

Session 2 · From problem to MVP

10

The metaphor comes from Ward Cunningham, in a short experience report on the WyCash software presented at the 1992 OOPSLA conference. Technical debt is not code written badly out of laziness: it is the deliberate choice to ship sooner with a temporary solution. Like a loan, it makes sense if you pay it back quickly; if you don’t, every minute spent on not-quite-right code counts as interest, paid again with every new feature (see also Martin Fowler, Technical Debt). For an MVP some debt is normal; the trouble starts when the company grows on top of that code. Question for the class: at what stage of a startup does it make sense to take on debt, and when do you have to pay it back?
